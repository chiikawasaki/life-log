# システム設計案

## 構成
React + TypeScript + ViteのレスポンシブSPA、Supabase Auth / PostgreSQLを使用する。
公開ページの検索最適化や独自サーバーが不要な個人用管理画面のため、まずSPAとする。
フロントエンドにはpublishable keyのみを渡し、service_roleやDBパスワードは含めない。

## Supabase選定理由
行動ルール・記録・ステータスの関係と、期間別集計をSQLで扱える。
外部キー・制約・トランザクション・RLSを使ってデータ整合性と所有者隔離を実現できる。
Firebaseでも実現可能だが、Firestoreでは集計や関連データの設計が異なる。
オフライン同期を重視するならFirebaseは有力だが、今回それはMVP外。
どちらも料金・運用上限はプロジェクト作成時のプランで確認する。

## データモデル
- statuses: id, user_id, name, display_order。所有者ごとに初期6項目を作成。
- activity_rules: id, user_id, name, status_id, archived_at。
- rule_versions: id, user_id, rule_id, unit, required_quantity, reward_points, created_at。作成後は不変。
- effort_entries: id（クライアント生成UUID）, user_id, rule_version_id, performed_on, quantity, note, created_at, updated_at。

数量は正の整数の最小単位（時間は分）とし、浮動小数点誤差を避ける。
他ユーザーのステータスやルールを参照できないよう、user_idを含む複合外部キーを用いる。
全テーブルでRLSを有効にし、SELECT/INSERT/UPDATE/DELETEをauth.uid() = user_idに限定する。
ルールは履歴があれば物理削除せずアーカイブ。版の編集は不可。

## 集計案
ルール版ごとに floor(累積数量 / 必要量) × ポイント を計算してステータスへ加算。
総合経験値は全ステータスのポイント合計。レベルは1 + floor(経験値 / 15)。
時系列の獲得量は対象期間末と開始直前の累積ポイントの差とする。
ルール版変更時には端数を旧版に残し、新版に異なる単位の数量を持ち越さない。
記録の削除・訂正は再計算に反映。ポイント残高を別途更新する方式は採らない。
計算は純粋関数として分離し境界値をテストする。以上は要件の仕様案確定後に実装する。

## 画面
ホーム：総合経験値・レベル・進捗バー、6ステータス、記録への導線。
記録：行動選択、実施日、数量、メモ。勉強時間は時間・分でまとめて入力し、整数の分に変換する。保存待ち・失敗・成功を明示。
履歴：日付順、訂正・削除。削除は確認あり。
ルール設定：行動の作成・新しい版の作成・アーカイブ。
振り返り：期間選択と日別の活動量。色だけで意味を伝えない。
認証：ログイン、ログアウト、セッション期限切れへの対応。

## 検証とレビュー
Vitest：数量の累積、閾値、レベル境界、版分離、訂正・削除、期間集計。
UIテスト：入力検証、二重送信防止、保存失敗後の入力維持、空状態。
Supabase接続後：認証、保存・再取得、別セッション間同期、匿名と別ユーザーのアクセス拒否。
ビルド・型チェックと、変更差分のセルフレビューを実施する。
RLS、秘密情報、他ユーザー参照、日付境界、データ消失を重点確認する。

## 成長ルールの境界例
レベルは経験値0〜14で1、15〜29で2、30〜44で3。
次レベルまでの必要経験値は15 - (総合経験値 % 15)。
勉強の初期値は120分で1ポイント。推奨する端数処理では90分で0ポイント・あと30分、続く30分で1ポイント、300分で2ポイント・あと60分となる。
