# MVPの検証とセルフレビュー

## 実施した検証

- TypeScript型チェック・Viteのプロダクションビルド。
- Vitest: 成長計算、入力・保存操作、PostgreSQLのアクセス制御を検証。
- Playwright: 1280pxのPC画面と360pxのスマホ画面でログイン→記録→訂正→振り返り→削除→再読込→ログアウトを確認。横スクロールとブラウザ例外がないことも確認。
- スマホ画面のスクリーンショットを確認し、実施日欄が狭くなる問題を修正。

ブラウザテストはテスト用APIを使用し、DBテストはPGlite（PostgreSQL）に実際のマイグレーションを適用して実施する。実プロジェクトのSupabase Auth / PostgRESTを含む統合テストとは異なる。

## レビューで確認・修正した項目

- 再送では同じUUIDを用い、upsertで重複を防止。応答が失われた後に入力を訂正して再送した場合も、訂正値が保存される。
- 記録の削除・訂正から経験値を再計算し、ポイント残高を二重管理しない。
- ルール版は書き換え不可。新しい版の端数と古い版の端数を混ぜない。
- ステータスはdisplay_order順に表示する。
- データ取得は500行ごとにページングし、APIの通常の1,000行上限で集計が途切れないようにする。
- RLSに加えて単一所有者を明示登録し、別の認証済みユーザーも拒否する。
- 複合外部キーと所有者確認で他ユーザーのルール参照を拒否する。
- 公開フロントエンドに含めるのはProject URLと公開キーだけ。DBパスワードは使用しない。
- SQLのsecurity definer関数はsearch_pathを固定し、公開実行権限を剥奪する。
- アーカイブされた行動の過去のポイントを保持する。

GitHub Actionsの結果はPR上で別途確認する。ローカル成功をCI成功とは扱わない。

## MVPの範囲と制約

- オンライン前提。別端末の更新はフォーカス復帰または手動更新で取得する。
- 記録全体をブラウザで集計する個人向け構成。大量データを扱う場合はサーバー集計に移行する。
- ルールの名前変更は過去の履歴の表示名にも反映する。過去のポイント・単位・閾値は変更しない。
- 所有者アカウント作成とパスワード回復はSupabaseの管理画面で行う。
